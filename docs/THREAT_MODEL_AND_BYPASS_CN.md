# MCAce 威胁模型与绕过边界

本文定义 MCAce 能证明什么、玩家能在本机修改什么，以及哪些证据可以触发当前连接动作。

## 目标

MCAce 向服务端提供 Fabric 客户端的有界视图，再把这个视图与独立的服务端行为证据关联起来。它能提供的核心事实是：

> 服务端收到了绑定当前 session 的客户端报告，并且可以把报告与服务端行为关联。

玩家可以控制客户端文件、JVM 参数、启动器进程、网络端点和本地内存。因此客户端报告不能证明 JVM、JAR、渲染器、操作系统或其他进程一定诚实。

## 协议能证明什么

协议使用 Ed25519 签名、随机 nonce、session ID、时间戳、递增序列、policy/manifest root 和 replay guard。这些机制保护报文完整性、session 绑定和重放防护。

客户端为当前连接生成临时签名密钥，并把公钥放进 `ClientHello`。服务端使用这个公钥验证后续帧。这能证明对端拥有当前 session 的密钥，不能证明密钥来自未修改的官方 MCAce 二进制。修改后的客户端或自定义协议客户端可以生成自己的密钥并签署假的报告。

SHA-256 用于文件和 manifest 完整性，CRC32C 用于传输校验，Ed25519 用于签名。未经审查的自定义 hash 不会改变信任边界：公开算法可以被重新实现，客户端内置的秘密可以被提取或拦截。

## 玩家可控的绕过方式

| 绕过方式 | 可行性 | MCAce 应产生的结果 |
| --- | --- | --- |
| 删除 MCAce | 高 | 服务器要求能力时进入 `ABSENT` 或限制准入 |
| 修改采集器或报告构造器 | 高 | 用玩家自己的密钥签署假的 `CLIENT_REPORTED` 报告 |
| 独立实现通信协议 | 中到高 | 获得有效 session 报告，但没有官方代码证明 |
| 认证后再加载外挂 | 高 | 依赖动态新鲜度和服务端行为检测 |
| 改名或重打包 Xray 材质包 | 高 | 精确 ID/hash 规则可能无法命中，行为信号仍可能命中 |
| Java Agent、原生 hook、渲染器外挂、外部进程 | 高 | ModList 采集器看不到，只有服务端行为可以辅助识别 |
| 重放旧报文 | 低 | 被 nonce、时间戳、session 和序列检查拒绝 |
| 模仿正常移动或挖矿 | 中到高 | 取决于独立行为检测器 |

最容易的伪造方式是用玩家自己的 session key 签署一份干净报告。攻击者不需要破解 SHA-256。服务端必须把客户端来源的事实保留为 `CLIENT_REPORTED / LOW`，直到独立 provider 或明确的管理员审查提供更高 authority。

## 信任和动作

| 状态 | 来源 | 可执行影响 |
| --- | --- | --- |
| `ABSENT`/`UNTRUSTED` | 客户端通道缺失、无效或不支持 | 限制准入或拒绝连接 |
| `CLIENT_REPORTED` | ModList、资源包、Shader 或文件观察 | 记录、提示、警告、挑战 |
| `STALE` | 在配置窗口内没有新鲜报告或心跳 | 新鲜度提示或配置的临时限制 |
| `SERVER_CORRELATED` | 客户端报告与同一 session 的服务端信号 | 限制功能或进入复核队列 |
| `SERVER_CONFIRMED` | 已认证的独立服务端 provider | 当前连接隔离或拒绝 |
| `ADMIN_REVIEWED` | 有记录的管理员决定和精确证据 | 带审计和回滚的当前连接动作 |

客户端静默不应自动生成作弊结论。它应使新鲜度租约过期，并取消依赖当前客户端视图的功能。现有心跳实现已经提供 `ACTIVE`、`STALE`、`MISSING` 状态、重放检查，以及连续缺失次数触发的可选临时控制。

## 加固顺序

1. 让心跳新鲜度继续绑定认证 session。有效帧刷新租约，非法、重放或过期帧不能刷新租约。
2. 把 `STALE` 当作运行状态。要求当前遥测的策略不能继续使用旧 inventory snapshot。
3. 尽可能把精确 Mod ID、文件 hash、content root 和行为规则放在服务端。客户端只接收采集范围和 policy 身份，不接收完整检测目录。
4. 客户端 artifact 观察只有在 Paper/Folia、Grim、Vulcan 或其他独立 provider 提供事件后，才能执行 `LIMIT`、`QUARANTINE` 或 `DENY`。
5. 增加自生成密钥、伪造干净图、重放、认证后静默和改名资源包夹具。伪造干净报告的预期结果是通信认证成功，但不产生 `SERVER_CONFIRMED`。
6. 将签名 Launcher token 作为可选后续信任层。用户态 Launcher 可以提高普通模拟成本，但不等于平台证明。TPM 或 OS attestation 属于单独的产品和兼容性决策。

## 源码与混淆

源码是否公开是产品和审计选择。公开协议、采集边界、威胁模型和测试向量有利于服务器管理员审计。服务端规则目录和签名密钥可以保持私有，以提高针对性绕过成本。JAR 一旦发到玩家机器上，源码可见性都不能证明客户端诚实。

客户端可以选择性混淆，用于保护实现和延缓普通修改。Fabric entrypoint、Mixin metadata、协议字段、build ID 和诊断信息必须保持稳定。服务端私钥和安全关键共享密钥不能放进客户端。混淆不应成为当前 MCAce 信任模型的发布门槛。

## 证据边界

可执行 live fixture 证明客户端与服务端的关联链路及干净对照。它不执行第三方外挂代码，不扫描任意操作系统进程，也不能证明公网 precision/recall。截图可以展示客户端状态，不能独立证明 Xray 或外部外挂正在运行。
